# M01 客户端应用框架 模块设计 v1.0

> **职责**：桌面客户端的公共底座——Electron 壳与进程拓扑、Renderer/Main/sidecar 拉起与崩溃监督、better-sqlite3 本地库与迁移、更新通道与 sidecar 版本锁死、Chromium 首启下载、通知分发、多窗口宿主。
>
> **上游依据**：`02-技术架构.md` v8.1 §6.1、§12.3、§13（另：§3.2 更新通道、§6.3 会话恢复、§10.2 激活校验）；`01-产品文档.md` v14.1 §1.1、§11。
>
> **状态**：起草（2026-10-14）。**全部客户端模块（M02/M03/M04/M09 客户端侧）的宿主与公共前置。**


## 1. 职责与边界

| IN（本模块负责） | OUT（不属于本模块） |
|---|---|
| Electron 壳与进程拓扑（架构 §6.1 客户端半区） | 任务执行语义与会话状态机（M05） |
| Sidecar / 本机认证器 / Block Update Service 的拉起与崩溃监督 | 浏览器自动化与 Chromium 进程内行为（M06） |
| 本地库 better-sqlite3：schema、迁移、备份（架构 §12.3 全表底座） | 各业务表的读写语义（归属模块自有） |
| 客户端更新（electron-updater）与 sidecar 版本锁死执行 | 积木 patch 更新策略/验签/灰度/回滚（架构 §3.2，M10/M05） |
| Chromium 首启下载（HTTPS + 哈希校验） | 商店/Library/运行中心 UI（M03）、画布 UI（M02） |
| 通知中心：本地事件 + 服务端推送的分发与路由 | 挂起/失效判定的业务来源（M16/M11） |
| 多窗口管理与窗口宿主（运行中心/创作者中心/交互面板/内嵌浏览器） | 模型与凭证（M04）、认证器业务逻辑（M09） |
| **任务调度器 TaskScheduler**：定时/队列任务的调度与触发（PRD §4.4；触发时调用 M05 `task.submit`；M03 为其管理 UI） | 任务执行语义与状态机（M05，只做执行） |
| 本地日志管道（JSONL 采集 + 脱敏挂点）、客户端侧 Sentry 接入 | 服务端日志与审计归档（M10/M12） |

**核心不变量**：
1. **版本锁死**：sidecar 版本与客户端版本由 manifest 声明锁死，不匹配拒绝启动；sidecar 更新只随客户端更新通道（对齐 M05 §5）；
2. **崩溃不丢会话**：被监督进程崩溃后的恢复一律基于 SQLite 持久化上下文的节点级 checkpoint 重跑，不承诺组件内恢复（架构 §6.3）；
3. **未验签不执行**：客户端更新验签失败拒绝安装；Chromium 下载哈希校验失败拒绝启用；
4. **Renderer 最小能力面**：无 Node 能力，仅 contextBridge 白名单 IPC；SQLite 仅 Main 侧访问。


## 2. 组件分解

```text
Electron 客户端（M01 壳）
┌────────────────────────────────────────────────────┐
│ Renderer（每窗口一进程，React 18 + TS）              │
│   · 主窗口（商店/Library，M03 UI）                   │
│   · 运行中心窗 / 创作者中心窗（M03/M02 UI 宿主）      │
│   · 交互面板小窗（两族控件渲染归 M03/M16）            │
│   · 内嵌浏览器窗（驱动归 M06）                       │
│ Main（Node）                                        │
│   · WindowManager + IPC Router（contextBridge）      │
│   · ProcessSupervisor（拉起/监督/重启/放弃）          │
│   · StorageService（better-sqlite3 + 迁移/备份）     │
│   · UpdateService（electron-updater，验签）          │
│   · ChromiumFetcher（首启下载 + 哈希校验）           │
│   · NotificationCenter（本地事件 + 服务端推送分发）    │
│   · TaskScheduler（定时/队列调度 → task.submit）      │
│   · LogPipeline（JSONL 采集 + 脱敏挂点 + Sentry）    │
└──────┬──────────────────────────┬──────────────────┘
       │ named pipe / Unix socket │ 拉起/监督（HMAC 会话密钥）
┌──────▼──────────┐  ┌────────────▼──────────────────┐
│ Runtime Sidecar  │  │ 本机认证器（M09 业务）          │
│ （M05，含 Egress │  │ Block Update Service          │
│  Proxy / DAG）   │  │ （策略见架构 §3.2，宿主在此）   │
└──────┬──────────┘  └───────────────────────────────┘
       │ 自管子进程树：组件 venv 进程 / Chromium（M05/M06 监督）
┌──────▼─────────────────────────────────────────────┐
│ app.db（SQLite：架构 §12.3 客户端全表）               │
└────────────────────────────────────────────────────┘
```

监督边界：M01 监督 sidecar / 认证器 / 更新服务三个直接子进程；sidecar 内部的组件 venv 进程与 Chromium 子树由 M05/M06 自管，M01 只消费其健康事件。


## 3. 关键流程

### 3.1 冷启动序列

```text
Main 启动
  → 单实例锁（二次启动 → 聚焦已有实例并路由参数）
  → StorageService：schema_version 比对 → 前向迁移（迁移前整库快照）
  → 进程清单校验：sidecar manifest 版本锁死
      （不匹配 → 提示更新客户端，拒绝拉起 sidecar）
  → 拉起 sidecar（会话密钥协商，机制见 M05 §5）
  → 在线激活校验触发（**支付成功即时触发为主，本序列为兜底**；
      时间戳留痕；与运行上报开关无关，架构 §10.2；校验逻辑与 M10 对接）
  → 窗口恢复（上次布局）+ 通知中心同步（服务端推送 + 本地挂起任务）
```

离线可用性：本地保留最后可用积木版本（PRD §3.4），启动不依赖网络；仅在线功能（商店/更新/推送）降级提示。

### 3.2 崩溃监督与恢复

| 监督对象 | 崩溃处理 |
|---|---|
| Runtime sidecar | 自动重启 → 从 SQLite 读会话上下文 → 节点级 checkpoint 恢复（M05 §7）；waiting_user/suspended 任务恢复原状态，交互上下文不丢 |
| 本机认证器 | 认证批次中止并保留现场，引导重试（流程语义归 M09） |
| Block Update Service | 中止本次更新，effective 版本保持不变（回滚语义见架构 §3.2） |
| Renderer（窗口级） | 重建窗口，状态经 Zustand + SQLite 恢复 |

- 连续崩溃上限与退避策略：TBD（模块细化时定）；超限停止自动重启，产生 `runtime_crashed`（→ failed，归因 unknown）并引导上报；
- 崩溃报告经 LogPipeline 脱敏后上传（Sentry）。

### 3.3 更新通道与版本锁死

- 客户端更新：electron-updater，平台签名更新源；验签失败拒绝安装；
- sidecar 随客户端包分发，版本锁死由 manifest 声明（M05 §5）：更新客户端 = 客户端与 sidecar 原子切换，二者不存在单独更新路径；
- 应用时机：存在运行中/挂起任务时不强制切换，待任务到达终态后应用（细则 TBD（模块细化时定））；
- Block Update Service（积木 patch 通道）：本模块仅提供进程宿主与调度窗口（运行中任务不热替换，下次运行生效——架构 §3.2）；前置条件校验、验签、smoke、灰度、回滚均消费 M10/M05 的签名元数据。

### 3.4 Chromium 首启下载

```text
触发：首启 / sidecar 声明的 Chromium 版本本地缺失
  → 取平台签名清单（版本 + sha256 + URL）
  → HTTPS 下载（Main 执行，尊重用户自配代理；断点续传）
  → 哈希校验通过 → 落盘启用；失败 → 丢弃并保留旧版本，可重试
  → 未就绪期间：浏览器类功能入口置灰并提示，其余功能不受影响
```

安装包不含 Chromium（目标体积 200-300MB，架构 §13）；下载进度入通知中心。

### 3.5 通知系统

| 来源 | 事件例 | 动作 |
|---|---|---|
| 本地（M16 会话事件） | 进入 suspended（72h 恢复窗口）、浏览器会话挂起 2h 关闭预告、恢复窗口临近超窗 | 系统通知 + 站内；点击直达交互面板 |
| 服务端推送（M11/M10） | 积木失效通知、下架应急通知（PRD §12.2）、废弃提前通知（PRD §13.2） | 系统通知 + 站内；点击直达应用详情 |
| 系统自身 | 更新就绪、Chromium 下载进度、崩溃引导 | 站内为主 |

- 分级配置入口在设置（PRD §11：账户、通知、数据清理、版本更新、关于）；关键类（挂起、下架应急）不可关闭——分类清单 TBD（模块细化时定）；
- 服务端推送通道与回执 API 由 M10 提供，本模块只负责拉取/接收与分发，不产生业务判定。

### 3.6 多窗口

- 窗口清单：主窗口、运行中心窗、创作者中心窗、交互面板小窗（置顶）、内嵌浏览器窗、设置窗；UI 内容分别归 M03/M02/M06，M01 拥有窗口生命周期与焦点路由；
- 交互面板与内嵌浏览器窗独立于主窗口存活：挂起任务不因主窗关闭而丢失入口；
- 窗口布局持久化；second instance 聚焦已有实例并路由参数（如通知点击的目标页）。


## 4. 数据模型

SQLite 单库 `app.db`；M01 拥有 schema 与迁移框架，业务表由归属模块读写（表清单 = 架构 §12.3）：

```text
migrations(id, version, applied_at)                 # 迁移账本
notifications_local(id, kind, source, payload_json,
                    read_at, created_at)            # 站内通知
crash_events(id, process, event, ts, report_uri)    # 崩溃监督审计
window_state(name, bounds_json, updated_at)         # 窗口布局

── 业务表（归属模块，M01 只管 DDL/迁移/备份）──
tasks / task_steps / artifacts / interactions       # M03/M16
library / blocks_local / block_locks                # M03（缓存与 effective）
credentials / auth_sessions / model_providers       # M04
recordings / certification_reports                  # M07/M09
grants / settings                                   # M05 / 各模块
```

- 迁移规则：只向前迁移；迁移前整库快照；迁移失败回滚快照并阻止运行任务启动（防脏库）；
- 业务表清单**随模块文档增量同步**（当前新增：M02 `modules_lib/creation_sessions/c0_drafts`、M04 `model_usage/budget_rules`、M08 `agent_sessions/parameterize_runs/draft_debug_runs`——DDL 语义归归属模块，M01 只管迁移框架与备份）；
- 数据清理：设置中的清理入口由 M03 呈现，删除执行在 M01（按表归属白名单）；交互记录留存策略说明随隐私政策展示（PRD §11）。


## 5. 接口

**Main ↔ Renderer（contextBridge 白名单）**：
- `window.*`：open/focus/close/route（窗口与通知点击路由）
- `app.*`：getVersion、quitAndInstall（更新）
- `notify.*`：list/markRead/preferences
- Renderer 不直接触达 SQLite；业务数据经各模块 Main 侧 service 的白名单 IPC。

**本地进程控制（M01 内部）**：
- `supervisor.start/stop/health(process)`——sidecar / 认证器 / 更新服务
- `chromium.ensure() → {version, path, sha256}`
- `update.check/apply()`（含 sidecar manifest 校验结果）

**对外（消费）**：服务端 notifications 拉取与回执（M10）；签名更新源（M10 分发）。


## 6. 依赖与被依赖

- 依赖：M05（sidecar 进程契约、通道安全、日志格式与脱敏引擎配置）、M10（更新源与 notifications API）、M16/M11（通知事件来源语义）、M06（Chromium 版本要求来源）。
- 被依赖：M02/M03/M04/M09（客户端侧宿主与存储底座）、M05（sidecar 拉起与监督执行方）、M06（窗口宿主）。


## 7. 验收标准

1. 版本锁死：篡改 sidecar manifest 版本 → 拒绝拉起并引导更新客户端；不存在 sidecar 单独替换后仍可启动的路径；
2. 崩溃恢复：运行中终止 sidecar → 自动重启且任务按 checkpoint 节点级恢复；waiting_user/suspended 任务状态与交互上下文保持；
3. 持续崩溃：达到上限后停止自动重启，产生 `runtime_crashed`（→ failed）并引导上报；
4. Chromium：哈希不匹配/传输损坏 → 拒绝启用且保留旧版本；断点续传与断网重试可用；
5. 更新：验签失败的更新包拒绝安装；更新前后 schema 迁移兼容（旧库升级回归通过）；
6. 通知：进入 suspended 产生系统通知且点击直达交互面板；服务端失效通知在客户端呈现并正确路由；
7. 多窗口：主窗关闭后挂起任务的交互面板仍可唤起；second instance 聚焦并路由；
8. 安全基线：Renderer 无 Node 能力（代码审查 + 用例）；SQLite 文件权限限本用户。
