# M12 Web 管理后台 模块设计 v1.0

> **职责**：平台运营四角色工作台——应用/积木审核与下架应急、C1 抽查工作台、合规声明重点审核、仲裁与保障金池赔付审批、退款冲正与结算对账、审计日志与运营位管理。
>
> **上游依据**：`01-产品文档.md` v14.1 §9.4、§12、§13.1-13.2、§16.1；`02-技术架构.md` v8.1 §10、§12.1；`03-模块设计/M09-认证流水线.md` §3.4（spotcheck_tasks）。
>
> **状态**：起草（2026-10-14）。阶段 2 提供最小集（审核/应急/审计），阶段 3 全量（保障金池全运行）。


## 1. 职责与边界

| IN（本模块负责） | OUT（不属于本模块） |
|---|---|
| 四角色权限矩阵与后台账号治理 | 审核标准与协议条款本身（后台只承载流程） |
| 应用与积木审核工作台（五项清单） | 认证执行与报告生成（M09） |
| C1 抽查工作台（spotcheck_tasks 全生命周期 UI） | 抽样生成与比对算法（M09 SpotcheckService） |
| 下架应急 SOP（delisted + 用户通知推送） | 商品状态机与数据（M10，后台发命令） |
| 仲裁与赔付：disputed 争议处理 / 失效归因复核 / 保障金池赔付审批 | 健康归因判定（M11，本模块消费证据） |
| 退款冲正审批、订单结算对账、发票入口 | 台账与冲正分录存储（M10 结算域） |
| 审计日志（≥3 年归档；认证报告随版本归档检索入口） | 认证报告归档存储本体（M09/M10 对象存储） |
| 运营位管理：分类/公告/推荐/活动 | 排序执行与健康分曝光计算（M10/M11） |

**核心不变量**：
1. 后台一切写操作落 `audit_logs`（操作者/时间/对象/前后状态），审计记录与认证报告归档保存 ≥3 年；
2. 金额一律「分」、时间一律 UTC ISO8601；退款/赔付/回补只以冲正分录实现，后台不存在修改原始分录的入口；
3. 权限矩阵在服务端强制（前端仅渲染收敛），越权请求拒绝并记安全事件；
4. 争议期 7 天、失效归因档位等规则数字不可后台配置化改动。

## 4. 关键流程

### 4.1 应用与积木审核流（in_review 工作台）

审核清单五项逐项核验（架构 §10.1），全部通过方可批准：
1. **认证报告核验**：certification_runs 报告（live/regression 分列、N、环境指纹、verdict）；C1 报告附 attestation 签名与抽查状态；
2. **站点合规声明**：compliance_declarations 核验；"高变更 + 个人信息输出 + 对外发布"三要素叠加 → 限制上架或人工重点审核，重点审核要求逐项确认数据类型与发布动作；
3. **AI 生成内容标识**：对外发布类内容必须可标注；
4. **confirm 覆盖**：发布类调用无对应 confirm 交互 → 审核不通过（M07 静态检查结果，后台复核）；
5. **权限最小化**：permissions_max 与声明确用比对复核。

状态机（架构 §10.1）：`draft → submitted → certifying → in_review → approved → published`；certifying 未达阈值 → rejected（附认证报告）→ 修订后可重提；in_review 环节驳回的状态转移 TBD（模块细化时定，与 M10 状态机对齐）。

### 4.2 C1 抽查工作台（对接 M09 spotcheck_tasks）

| 状态 | 工作台动作 |
|---|---|
| pending | 抽查队列查看（每 10 份 C1 报告至少 1 份，M09 生成）、重测任务下发确认 |
| accepted / streaming | 重测执行实时监控（流式上报） |
| done | 报告比对视图：步骤序列 / 时序分布 / 网络行为形状 vs 原报告（compare_json） |
| mismatch | 处置：积木版本下架（delisted）+ 转入保障金池流程 + 引用应用标记"积木维护中"（不直接下架应用） |
| timeout（14 天未响应） | 归入"创作者超期未响应"归因档（架构 §10.3） |

### 4.3 下架应急 SOP

```text
触发：安全事件规则命中（egress_denied / permission_denied /
      update_permission_escalation 等，PRD §14）或审核员人工上报
  → 创建应急工单（审核员，必填事件引用与影响面初判）
  → 执行下架：目标应用/积木版本 published → delisted（立即生效）
  → 用户通知推送（notifications）：
      涉应用 → 通知已购买家；涉积木 → 引用应用标记"积木维护中"
  → 处置分流：退款/保障金池评估（4.4）或修复重发布流程
  → 全程 audit_logs 留痕 + 复盘记录归档
```

### 4.4 仲裁与赔付

```text
退款/失效争议 → 台账置 disputed（争议期 7 天，平台仲裁）
  → 证据视图：订单、认证报告（版本归档）、健康归因记录、
    用户运行上报聚合统计（不含页面内容）
  → 失效归因复核（四档，架构 §10.3）：
      站点变更（非创作者过错）→ 释放暂停，修复后恢复，不转入保障金池
      创作者超 14 天未响应     → 未释放份额转入保障金池
      平台积木缺陷            → 不罚创作者；平台赔付（保障金池资金优先，不足平台承担）
      废弃                    → 剩余释放暂停；已购保留本地使用权；维护期内退款平台承担
  → 保障金池赔付审批（财务）→ 冲正分录入 guarantee_pool_ledger
  → 创作者申诉工单处理（申诉流程见创作者协议）
```

### 4.5 退款冲正审批

- 退款来源三类（PRD §13.1，激活口径以架构 §10.2 为准）：① 购买后 24h 内未完成在线激活校验 → 全退（完成激活即视为已开始使用，不再适用 24h 全退）；② 维护期内积木失效超 7 天 → 按剩余维护月份比例退款（失效判定以健康归因为准，user-side 类不算失效）；③ 争议裁决退款；
- 冲正规则：台账只增不改，每笔冲正关联原始订单与归因记录；①类是否免审批自动执行 TBD（模块细化时定，与 M10 口径对齐）；
- 资金追回顺序（架构 §10.3）：① 该订单未释放保证金优先冲抵 → ② 创作者未结算余额冲抵 → ③ 不足部分记平台垫付应收。

### 4.6 订单结算对账

```text
订单支付 → 平台 30% / 创作者 70%
  创作者侧：80% 可结算（跨过 24h 退款窗 + 7 天争议期后可提现；提现前实名认证）
           20% 维护保证金，双月释放一期 × 6（对齐 12 个月维护期）
对账：订单 ↔ settlement_entries ↔ guarantee_pool_ledger 三方平衡报表
     + 差异清单与处理工单；发票入口（规则见创作者协议）
```

### 4.7 运营位管理

- 分类（categories）、公告（announcements）、推荐位与活动配置；
- 曝光策略配置：健康分影响曝光、修复响应时效仅作曝光微调因子（PRD §10.2）——计算与排序由 M10/M11 承载；免费应用限制橱窗位（PRD §13.1）。

## 6. 接口（后台 BFF，/admin/api）

- 审核域：`GET /review/queue`、`POST /review/{subject}/verdict`（逐项清单结果 + 批准/驳回）；
- 抽查域：`GET /spotcheck/tasks`、`GET /spotcheck/{id}/compare`、`POST /spotcheck/{id}/disposition`；
- 应急域：`POST /emergency/delist`、`POST /emergency/notify`；
- 仲裁财务域：`GET|POST /arbitration/*`（disputed 工单）、`POST /finance/refund-reversal`、`GET /finance/reconciliation`；
- 运营域：`/ops/categories|announcements|recommendations`；
- 审计域：`GET /audit/logs`（按对象/操作者/时间检索）；
- 后台登录与账号治理（登录方式、会话策略）TBD（模块细化时定）。


## 7. 依赖与被依赖

- 依赖：M09（认证报告、抽查任务与处置命令）、M10（商品状态机、订单、结算与冲正服务、通知通道）、M11（健康归因证据）。
- 被依赖：M09（抽查处置入口）、M10（审核决策驱动上架状态机）、创作者侧（申诉工单流转）。


## 8. 验收标准

1. 权限矩阵服务端强制：四角色越权访问全部拒绝并记安全事件；
2. 审核流：五项清单逐项核验留痕；三要素叠加应用强制进入人工重点审核路径，未逐项确认不可批准；
3. 抽查：pending → 下发 → 流式监控 → 比对 → mismatch 处置全链路可演示，处置联动积木 delisted、引用应用"积木维护中"标记与保障金池流程工单；
4. 应急 SOP：一次安全事件触发的 delisted → 用户通知推送演练通过，全程 audit_logs 留痕；
5. 仲裁：disputed 争议期 7 天工单流转正确；四档失效归因各自触发正确资金动作（释放暂停 / 转入保障金池 / 平台赔付 / 废弃暂停）；
6. 冲正：任意退款/赔付生成冲正分录且原始分录不可修改；资金追回顺序三步依序执行；
7. 对账：订单-分录-池三方平衡报表输出，差异清单可追踪；金额字段全量「分」校验通过；
8. 审计：全部写操作有 audit_logs 记录；认证报告随版本归档可检索，≥3 年归档策略生效。
