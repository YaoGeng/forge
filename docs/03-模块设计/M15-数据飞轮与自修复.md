# M15 数据飞轮（二库）与声明式自修复 模块设计 v1.0

> **职责**：把平台运行中产生的结构知识与失败知识沉淀为两个数据集（页面结构特征库 page_structures、失败模式库 failure_patterns），并以声明式变更（selector 配置/参数/prompt 文案）编排自动修复——触发 → 候选生成 → 回归 → 创作者确认 → 签名 patch → 灰度传播，修一个积木、所有引用应用恢复。
>
> **上游依据**：`02-技术架构.md` v8.1 §3.3、§9、§12.2；`01-产品文档.md` v14.1 §6.3、§6.4。
>
> **状态**：起草（2026-10-14）。二库随 M06/M09/M11 数据流先行建设；声明式自修复按 PRD §15 为阶段 4 交付。


## 1. 职责与边界

| IN（本模块负责） | OUT（不属于本模块） |
|---|---|
| page_structures：DOM 结构、selector 稳定性、变更频率（无访问控制类字段） | 健康检测执行与调度（M11，消费本库） |
| failure_patterns：failure_class、env_class、修复记录、确认状态 | 认证流水线执行（M09，certification_runs 由其写入） |
| certification_runs 消费（可靠性主数据集，只读） | 用户运行上报采集管道（M11，本模块只消费聚合结果） |
| 自修复链路编排（触发→候选→回归→确认→发布委托→回写） | patch 签名与灰度通道执行（M10，本模块只发起委托） |
| 修复历史回写 failure_patterns | 保障金池账务与赔付审批（M10/M12，本模块提供归因依据） |
| unknown>30% 告警联动 | 管理后台工作台 UI（M12） |

**核心不变量**：
1. page_structures 入库前过字段白名单：任何访问控制类字段（Cookie、登录态、账号标识、凭证句柄）不得入库——校验失败拒收并告警；
2. 自动修复候选仅限 change_kind=declarative（selector 配置、参数、prompt 文案）；代码级变更不进自动通道，一律转 minor/major 重认证（PRD §9.6）；
3. 无"回归通过 + 创作者确认"不发布——自动通道的终点是待确认候选，不是已发布版本；
4. 已发布修复必须回写 failure_patterns（修复记录 + 确认状态），未回写视为工单未关闭；
5. certification_runs 只读消费，不复制、不改口径（live/regression 分列）。

## 3. 关键流程

### 3.1 数据流入（二库写入）

| 数据集 | 写入方 | 内容 | 约束 |
|---|---|---|---|
| page_structures | M06 站点结构检测（主）、M11（公开页稳定性信号）、M09（认证批次附带） | DOM 结构摘要、selector 候选与稳定性、变更频率、访问稳定性信号 | 检测礼仪内采集；字段白名单 |
| failure_patterns | M11（检测/用户上报归因）、M09（认证失败归因）、本模块（修复历史） | failure_class × env_class、出现聚合、修复记录、确认状态 | security 类单列，不入本表统计分母 |

### 3.2 certification_runs 消费方式（只读）

① 按站点/积木聚合 live_pass_rate 时序 → 站点变更分级校准与认证阈值调优输入（供 M09）；② fail_json 失败明细归纳 → 补充 failure_patterns 模式样本；③ 环境指纹聚合 → 认证环境矩阵参考（PRD §6.3 消费方）。本模块不写该表、不另建可靠性表。

### 3.3 声明式自修复链路（架构 §3.3）

```text
触发：Health 检测异常（M11）/ 用户运行上报聚合超阈值（M11；含登录积木的主信号）
  → RepairOrchestrator 建修复工单
  → 候选生成（仅 selector 配置 / 参数 / prompt 文案）
      · selector：优先 page_structures 中稳定性最高的候选
      · 参数 / prompt 文案：依据失败归因（timeout / 输出偏差类）
      · 规则匹配优先，LLM 辅助（平台质量活动口径，PRD §5.1）；生成策略 TBD（模块细化时定）
  → 回归：
      C2（无登录）→ 平台沙箱 golden 回放（mock 网络存根——验证逻辑，不验证站点真实状态）
      C1（含登录）→ 创作者本机回归（创作者触发，复用 M09 本机认证器环境，凭证不出本机）
  → 创作者确认（修复工作台：diff 预览 + 回归证据）
  → 委托 M10：签名发布 patch 版本（发布侧 declarative diff 强制校验）
  → 灰度传播（5% → 50% → 100%，按引用应用分批；任一批次 smoke 失败率超阈值冻结回滚；
             运行中任务不热替换，下次运行生效）
  → 引用应用恢复（一次修复全体恢复）
  → 修复历史回写 failure_patterns（confirmation_status=confirmed）
```

### 3.4 候选硬边界（代码级变更无自动出口）

- 候选 diff 经文件级白名单校验：仅声明式资源（selector 配置、参数、prompt 文案）；
- diff 含任何代码文件 → 候选作废，工单升级 `escalated_minor`：转 minor/major 版本流程（M09 重新认证真实运行 N≥20 + 应用创作者重新发布，PRD §9.6），并通知创作者；
- patch 权限集不得扩大（违反即拒绝，`update_permission_escalation` 记安全事件，M10 通道强制）；
- 复合积木：修复目标是其内层原子积木时，patch 按应用侧展开的 lock 条目走正常通道传播；复合积木自身 `patch_window=null`，仅整体重发布（架构 §2.5）。

### 3.5 回归失败与工单治理

- 回归失败 → 候选标记失败入修复记录 → 重新生成（尝试次数上限 TBD（模块细化时定））→ 超限关闭工单并通知创作者人工处理；
- 创作者拒绝确认 → 工单关闭（rejected）；
- 工单超期未响应信号同步 M10（对应失效归因分级处置，见 3.6）。

### 3.6 归因对接（保障金池与不罚创作者）

修复工单的归因结论（failure_patterns 记录链）作为 M10 失效归因分级处置依据：

| 归因 | 处置（M10 执行，本模块提供依据链） |
|---|---|
| 站点变更（非创作者过错） | 释放暂停，修复后恢复，不转入保障金池 |
| 创作者超 14 天未响应修复通知 | 未释放份额转入平台保障金池 |
| 平台积木缺陷 | 不罚创作者，由平台赔付（保障金池资金优先，不足部分平台承担） |

### 3.7 unknown>30% 告警联动

M11 月窗 unknown 归因占比 >30% 触发告警（PRD §14）→ 本模块联动：① 生成归因质量工单（错误码→failure_class 映射复核，映射表由 M09 维护）；② 标记认证阈值校准任务（M09）；③ 告警事件入 audit_logs（M12 可见）。


## 4. 数据模型

```text
page_structures(
  id, site_host, page_kind, url_pattern,
  dom_digest,                # 结构摘要（去内容）
  selector_candidates_json,  # 候选 selector + 稳定性分 + 命中率
  change_freq,               # 变更频率评分（站点变更分级输入）
  stability_signals_json,    # 响应状态 / 加载成功率（检测礼仪内采集）
  inspected_at,
  source                     # site_inspect / health_check / certification_batch
)

failure_patterns(
  id, block_name, block_version,     # 版本按 lock effective 归因
  app_id,
  failure_class,             # selector_missing/timeout/auth_expired/captcha/network/unknown
  env_class,                 # device / network / account
  occurrence_json,           # 次数 / 时间窗 / 来源（health/user_report/certification）
  repair_record_json,        # 候选类型 / 变更摘要 / 回归结果 / 发布版本 / 尝试轮次
  confirmation_status,       # pending_creator / confirmed / rejected / escalated_minor
  created_at, updated_at
)

repair_orders(
  id, block_name, block_version,
  trigger_source,            # health_check / user_report_aggregate
  failure_refs_json,         # 关联 failure_patterns id 列表
  status,                    # candidate_ready / regressing / awaiting_confirmation /
                             # published / rejected / escalated_minor / closed
  candidate_json,            # 候选 diff（declarative 白名单内）
  regression_result_json,
  created_at, updated_at
)
```

certification_runs 表结构见 M09 §4，本模块只读。


## 5. 接口

**服务端 REST（/api/v1）**：
- `POST /flywheel/page-structures`（M06/M11/M09 写入，字段白名单校验）
- `GET /flywheel/page-structures?host=…&url_pattern=…`（M11 判定 / 候选生成消费）
- `GET /flywheel/failure-patterns?block=…&class=…`（归因查询）
- `POST /repair/orders`（触发：source + block/version + failure_refs）
- `GET /repair/orders/{id}`（候选 diff + 回归证据 + 状态）
- `POST /repair/orders/{id}/confirm` / `/reject`（创作者确认 / 拒绝）

**内部委托**：
- RepairOrchestrator → M09：回归执行请求（沙箱 golden 批次 / C1 本机回归任务下发）；
- RepairOrchestrator → M10：patch 发布委托（签名 + 灰度）+ 归因结论同步（保障金池分级依据）。

**客户端（创作者修复工作台，M02 内嵌）**：工单列表、diff 预览、回归证据查看、确认/拒绝、C1 本机回归触发。


## 6. 依赖与被依赖

- 依赖：M06（结构报告写入）、M09（certification_runs 数据源、回归执行、阈值调优协同）、M11（触发信号：health_checks 与用户上报聚合）、M10（Registry 发布/签名/灰度通道、归因处置）、M07（golden 回放器、declarative diff 校验规则）、M12（告警与工作台呈现）、**服务端平台 LLM 网关（候选生成的模型调用，平台自有账户——服务端内部组件，非 M04：M04 是客户端用户自配 Key 模块，平台质量活动不经用户 Key，PRD §5.1/§9.1）**。
- 被依赖：M11（page_structures 漂移判定支撑）、M09（阈值调优与站点变更分级输入）、M10/M12（归因依据链）、M02/M03（修复状态透出——"积木维护中"标记与其恢复）。


## 7. 验收标准

1. 字段白名单：构造含 Cookie/登录态/账号标识的入库请求 → 拒收 + 告警；page_structures 全表扫描无访问控制类字段；
2. 链路演示：一次 health 触发的 selector 修复端到端（触发 → 候选 → 沙箱 golden 回归 → 确认 → 签名 patch → 灰度 → 引用应用恢复 → failure_patterns 回写）；
3. 硬边界：候选 diff 混入代码文件 → 候选作废并升级 `escalated_minor`（转重认证建议），自动通道无代码级变更发布出口（审计可证）；
4. C1 路径：本机回归由创作者触发，凭证不出本机（复用 M09 认证会话隔离）；
5. 回写完整性：任一已发布 patch 在 failure_patterns 有完整修复记录（候选/回归/确认状态/发布版本）；
6. 归因对接：平台积木缺陷工单 → M10 按"不罚创作者"档处理的信号链路可查证；
7. 告警联动：构造 unknown 占比 >30% → 告警 + 归因质量工单生成 + audit_logs 留痕。
