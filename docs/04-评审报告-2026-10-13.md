## 1. 执行摘要

**一句话总判断**：PRD 的叙事是"买到就能跑"，交付机制却是"跑通一次就能卖"——上架门槛在统计上等于没有门槛，平台最值钱的类目（登录类工具）在认证、审核、健康三个环节全部不可测，且平台自身的服务端检测行为构成最大的法律暴露点。

**四个致命问题**（多视角独立得出）：

| # | 问题 | 出处 |
|---|---|---|
| F1 | 上架门 = "25 次重试内单次通过"，p=0.2 的工具通过概率 99.6%，筛选的是运气不是可靠性 | 产品 F1 / 架构 F1 / 澄清·隐藏意图1 |
| F2 | 凭证仅存本机 ⇒ 登录后流程在认证/审核/健康三个系统全部不可测，旗舰场景（小红书/1688）恰好全是登录类 | 产品 F2 / 架构 F2 / 澄清·问题1 / 法务 H1 |
| F3 | 买断制维护期限未定义 + 保证金"转没收"条款大概率被挑战——财务与法律两头必崩 | 产品 F3 / 法务 M2 |
| F4 | 平台服务端对强反爬站点的定时检测使平台自身成为高频自动化访问主体，是文档中最直接的法律暴露点 | 法务 H1 |

**如果只能改一件事**（产品经理结论）：把上架门从"单次通过"改成"统计认证，实测通过率带样本量印在详情页"。积木化、健康分、保证金、退款、定价全部是"可靠性可测量"的下游。

**最重要的交叉发现**：架构师的"服务端认证流水线"与法务的"平台不应做高频访问者"相撞，叠加上登录态悖论，唯一同时满足三方约束的路径是**认证分级执行**——low/mid 站点服务端沙箱认证；登录类/强反爬类走创作者本机认证 + 签名上报 + 服务端抽查。一石二鸟（登录态悖论 + 平台暴露）。


## 2. 共识问题（两个以上视角独立得出，可信度最高）

### 2.1 上架门槛统计上无效【致命】
- 单次通过不携带可靠性信息；25 次重试的实际效果是"把不可靠工具洗成已认证"，且最终"通过"只采样了最后一次代码版本在创作者机器（暖登录态、住宅 IP、单一输入）上的一个样本。
- **改法（三方一致）**：创作者侧"最终代码版本连续 k 次通过"（k≥3，零基础设施立即落地）；上架侧服务端统计认证（干净环境 N≥20 次，按站点分级设阈值）；通过率展示强制带样本量 N、时间窗、环境指纹。

### 2.2 登录态认证悖论【致命·前置决策】
- 凭证仅存本机（架构 §10.2）⇒ 平台沙箱永远测不了登录后流程 ⇒ "发布前统计认证"对最有价值的类目原理性无效。买家成为事实上的 QA 车队。
- **三条出路（没有第四条）**：① 创作者本机认证 + 签名上报 + 服务端抽查（过渡，可作弊需防）；② 平台自持测试账号池（长期，破凭证红线 + 法务暴露，仅在获站点授权时考虑）；③ 不认证登录流程、信任字段降级标注（承认旗舰类目无保障）。
- **综合结论**：① + ③ 组合先行，② 仅在有站点合作时重开。

### 2.3 副作用幂等缺失【致命·资损级】
- "发布评论"节点评论已发出但上报超时 → `component_timeout` 可重试 → 评论发两遍。UGC/交易场景真实世界损害。
- **改法**：`component.yaml` 增加 `side_effect` 声明（静态检查器强制）；DAG executor 持久化节点输出 checkpoint，续跑跳过已成功节点；**副作用节点禁止自动重试**，失败必须 `runtime.confirm` 人工确认；retryable 改为"错误码 × 副作用属性"二维判定。

### 2.4 "说一句话产出模块"降级，不是砍掉
- 买家不关心工具怎么来的——把最贵、最不可靠的能力放在信任链最上游是结构性错误。
- **改法**：对话式生成降级为"新积木草稿入口"，产出标"未认证"，私用放行、上架必过认证门。创作者第一卖点改为："拼认证积木 + 录一遍演示 = 上架级应用，通过率印在详情页"。

### 2.5 文档完整性缺陷
- M09（AI 测试 Agent）在架构附录 C 指向 §9.1，而 §9.1 是上架状态机——**认证环节恰好是整个架构唯一没被设计的模块，悬空**。
- `03-模块设计/` 不存在；PRD §0（含 Linux）vs §14（Linux 阶段 5）矛盾；"Chromium 随包" vs "首启下载"矛盾；两份文档标注"定稿"但含"待验证/新增（无目标值）"占位符——下游会把未决当已决。


## 3. 产品经理评审（senior-pm）

### 总判断
PRD 的叙事是"买到就能跑"，交付机制却是"跑通一次就能卖"。这道裂缝靠健康检测和保证金糊不住。**没有测量，就没有定价权。** 积木化方向明确支持。

### 【致命】

**F1. 上架质量门是"单次通过"，与核心承诺数学上不自洽**（§1.1、§8.1、§8.7、§8.8；架构 §9.1）
一个真实成功率 60% 的工具有 60% 概率通过这道门。上架门不筛选可靠性，只筛选运气。
改法：新增"认证规范"章节——干净沙箱独立运行 N≥20 次；low/mid 实测通过率 ≥90% 方可上架；high 级不设下限但强制展示实测通过率与测量环境；实测通过率即详情页初始可靠性分。承诺文案从"买到就能跑"改为"实测通过率印在详情页，跑不通按政策退款"——绝对化承诺不可交付，数字可交付。

**F2. 健康分对最高价值场景先天失明**（§9.1、§1.2；架构 §8）
越值钱的工具，"健康评分+最近检测时间"越没有数据。
改法：① 登录态流程认证——创作者一次性授权会话注入（需安全评审签字）或平台测试账号；② 健康分 = 认证通过率（初始）+ 买家上报成功率（滚动），两者分列且展示样本量；③ user-side 类失败不计入工具健康分。

**F3. 买断制的维护期限没定义，经济模型两头必崩一头**（§12.1、§12.2、§1.1；架构 §9.3）
若可退是终身的 → 第 8 个月工具死掉时钱已结算完；若 6 个月后不可退 → "坏了有兜底"是虚假承诺。
改法：显式定义"买断含 12 个月维护期"，详情页公示维护截止日；维护期内失效超 7 天按比例退款（缺口由平台 30% 抽成垫付——这就是抽成的风险对价，必须认）；维护期后转 as-is，创作者可续保。

### 【严重】

- **S1** "说一句话"当第一卖点：M08 估 60-100 人日 × 复杂度系数 2.0，价值对买家为零。降级为新积木草稿入口。
- **S2** 自修复"patch 热更新"超阶段且突破安全红线（"进程级沙箱不防蓄意"架构自己写的，这条管道就是攻击者最想要的通道）。一期自修复 = 检测+归因+通知+签名新版本；自动修复仅限声明式变更（selector 配置）；代码级热更新 ❌ 暂不做。
- **S3** 退款与失效仲裁规则缺失到不可执行。"没有仲裁规则的保证金制度 = 创作者关系定时炸弹"。补：失效判定以归因为准、争议期 7 天、平台仲裁、误判回补。
- **S4** 积木化地基问题没写：版本与应用依赖策略（.aapkg 把 modules 打进包里，修复如何到达买家？）。改：认证积木以引用打包，客户端按需拉取签名积木包；应用声明兼容版本区间。
- **S5** 演进路线把最贵最险的放最前（阶段 1 全量对话式生成），信任设施排阶段 3，积木库排阶段 5。
- **S6** 认证成本归属未定。积木认证平台承担（护城河投资）；应用认证每版本 1 次免费额度，复测收费。

### 【一般】
M1 定价建议/自动截图砍或 P2；M2 五星评分延后（实测通过率就是最好的评分）；M3 六库飞轮保留 2 库（站点指纹、失败模式）；M4 信任字段补"单次运行预估 Token 成本区间"+"维护期截止日"，所有比率带样本量；M5 免费应用同过认证门；M6 创作期调试上限砍到 ≤8 次，预算挪给认证期；M7 补"30 天退款率"（北极星，红线 <5%）+"认证一次通过率"；M8 废弃/下架时买家权益（已购保留最后版本本地使用权）。

### 方案对比

| 方案 | 做法 | ROI | 结论 |
|---|---|---|---|
| A 维持现状 | 对话式生成先行，无统计认证 | ≪1 | ❌ 明确不该做 |
| B 现状+认证门 | 保留 LLM 生成主线 + N 次认证 | <1（认证按应用版本重复发生，不沉淀为资产） | 退路 |
| C 积木化 | 认证积木 + 组装 + 录制参数化 + 统计认证 | >1（前置投资，边际成本递减；省掉 M08 前置的 120-200 人日） | ✅ 推荐 |

**结构差异比点数重要：C 贵的部分是一次性平台投资，A/B 贵的部分随应用数线性复发。**

### 积木化支持理由（四条）
1. 可靠性从不可知变为可测量、可定价；
2. 认证成本从 O(应用数) 降为 O(积木数)——才配得上 30% 抽成对应的平台责任；
3. 修复从 O(应用数) 降为 O(积木数)，"修一个全部恢复"让 6 个月保证金制度第一次变得可执行；
4. LLM 降级为装配工后，生成物从"代码"变为"配置/参数"，可静态校验，审核成本暴跌。

**反方风险**：积木覆盖面决定平台场景面，冷启动期 SKU 少。对策：10 个场景打透胜过 1000 个场景 60% 通过率；自定义节点做逃生舱（标"未认证"）。

### 演进路线改写建议

| 阶段 | 目标 | 关键交付 |
|---|---|---|
| 0 | 不变 | 不变 |
| 1 | **认证管线 + 种子积木库** | N 次认证管线、10 场景 20-30 个平台自营积木、平台手工组装 3-5 个应用 |
| 2 | **买家闭环** | Marketplace + 健康，只卖平台自制认证应用，验证"买到就能跑"的付费意愿 |
| 3 | **创作者开放** | 画布 + 录制参数化 + 创作者认证上架 |
| 4 | 生态 | 第三方积木市场 + 对话式生成（草稿入口）+ 声明式自修复 |
| 5 | 扩展 | 全 Adapter + Linux |

逻辑：先用平台自制应用验证买家愿不愿为"实测通过率"付钱——**买家不买单，创作者生态救不了场**。


## 4. 架构师评审（oracle）

### 底线结论
当前架构的核心问题不是"测试不够"，而是**可靠性在全链路上从未被定义为可测量的量**。积木化不是加几张表，而是要把"组件版本"提升为一等公民。

### 【致命】

**F1. 上架门槛统计上约等于无门槛**（§7.1-7.3、PRD 8.7/8.8、§9.1）
p=0.2 的工具 25 次内至少过一次的概率 99.6%。且每次 debug 都在改代码，最终"通过"只采样了暖登录态、住宅 IP、单一输入下的一个样本。
改法：① 创作者侧连续 k 次通过（k≥3，零基础设施）；② 上架必须过服务端认证流水线；③ 详情页通过率必须带 N、时间窗、环境指纹。

**F2. 凭证本机约束 vs 认证/auto_testing/Health 三方矛盾未解**（§10.2、§8、§9.1）
登录类工具的登录后流程在三个系统中全部不可测。
改法（三选一并写进架构）：① 创作者本地认证（凭证不出机、住宅 IP 真实，结果签名上报，服务端抽查复核防作弊）作为过渡；② 平台测试账号池作为长期；③ 不认证+降级披露为兜底。推荐 ①+②，**这是积木化认证能否成立的前置决策**。

**F3. DAG 重试/续跑无幂等与副作用语义**（§3.4、§4.2、附录 D）
`component_timeout` 可重试 + "发布评论"节点 = 评论发两遍。
改法：`side_effect` 声明 + 节点输出 checkpoint + 副作用节点禁自动重试 + retryable 二维判定。

**F4. 自修复"patch 热更新"与自包含 .aapkg 包模型根本冲突——修复传播机制不存在**（§6.4、§3.5、§9.4）
"修一个积木→所有引用工具恢复"要求组件可独立更新，则需要组件 registry、组件级签名、版本锁定、客户端更新通道、回滚——**当前一项都没有**。§6.4 的"热更新"五个字背后是半个分发系统。
过渡期降级为"应用级整包更新"，先让链路存在。

**F5. 出口代理只存在于错误码表——组件可绕过 AST lint 直接外泄登录后页面数据**（附录 D、§6.2、§4.5、§10.3）
AST lint 可被 `getattr`/`importlib`/动态构造绕过，进程沙箱不拦网络——任意组件可向攻击者域名 exfiltrate 用户隐私数据。**上架制市场 + 普通用户场景下最现实的攻击面。**
改法：所有组件进程强制经 egress proxy 出网，代理在网络层强制执行 `domain:<host>` 授权，与 PermissionBroker 构成"API 层 + 网络层"双闸。

### 【严重】
- **S1** 服务端 auto_testing 用数据中心 IP 测反爬站点，环境无代表性（认证环境指纹必须记录并披露）。
- **S2** waiting_user 持久化与恢复语义未定义：浏览器会话不可序列化；崩溃/休眠后怎么办；600s 超时对真实用户太短（离开 10 分钟 = 任务失败）。改：超时按交互类型分级（login/takeover 小时级，confirm 分钟级）且可续期；崩溃恢复 = DAG 节点级重跑。
- **S3** Agent debug loop 无成本熔断、无 best-so-far 回溯、失败指纹过粗（6 类无法支撑卡住判定）。25 轮 debug 在主流模型上是数美元到十几美元、20-40 分钟，全部创作者自付且无上限。改：ModelRouter 硬上限熔断 + 留存 best-so-far 耗尽时回滚 + 失败指纹细化到复合哈希 + 修复确认同样要求连续 k 次通过。
- **S4** CodeAct 动态生成代码绕过静态检查——必须显式声明 CodeActExecutor 与组件进程跑在同一 PermissionBroker + egress proxy 之下。
- **S5** 健康评分信号稀薄却与保证金/曝光挂钩；"修复响应时效"计入评分意味着"坏但修得勤"得分不低。改：分维度展示 + 无最小样本量显示"数据不足" + 修复时效只作微调因子。
- **S6** 依赖安装器与组件环境隔离完全未设计。改：每组件独立 venv + 白名单源 + 锁定哈希 + 安装期网络过 egress proxy。

### 【一般】
G1 sidecar 安全与生命周期（一次性 token 语义不清，建议 named pipe + ACL；Chromium 首启下载无完整性校验——供应链缺口）；G2 login 交互→凭证落库路径未定义；G3 退款判据可作弊；G4 公钥轮换无机制；G5 文档引用完整性（M09 悬空、三个"幽灵组件"只见于错误码表）；G6 三平台沙箱一致性工程量被低估；G7 演进路线未包含认证/积木化。

### 积木化最小架构改动清单（按依赖排序）

1. **通过判据统计化**（小，纯策略，先行落地不等其他）；
2. **对象模型扩展**（小-中）：`side_effect`、组件依赖声明、reliability 块、lock 文件 pin 版本、认证三档（公开页/登录流程/反爬 best-effort）；
3. **凭证策略修正案**（中，F2 前置决策）：区分"用户凭证（本机，不变）"与"认证会话（授权/平台账号，加密存储、仅认证、可撤销）"；
4. **认证流水线子系统**（中-大）：录制回放回归（golden run 的 DOM/network 经 CDP 录制，重放，便宜且确定）+ 少量 live 探测；`certification_runs` 表同时成为数据飞轮的可靠性主数据集；
5. **组件级签名与 registry + 客户端更新通道**（中-大）：patch 级自动更新的前置条件 = 接口 semver 兼容 + **权限集不扩大**（否则热更新变成提权后门）+ 验签 + 本地 smoke test + 失败回滚；
6. **健康系统按组件版本维度重构**（中）；
7. **执行语义补丁**（小-中）：F3 幂等 + S2 恢复语义 + S3 预算熔断——这三项不依赖积木化，独立先行。

**升级触发条件**：强反爬登录类成为收入主体 → 需住宅代理认证池或创作者本地认证升级为主通道；热更新被滥用 → 认证签名密钥与分发签名密钥分离 + 灰度。

### "写了但很难实现" vs "没写但必须定义"
- **很难实现**：§6.4 热更新（无分发机制）；§5.5 high 级"完整支持"（军备竞赛，承诺过强）；§9.1 登录后页面变化检测（与自述边界矛盾）；服务端 auto_testing（环境无代表性）。
- **没写但必须定义**：认证统计判据与环境指纹；认证凭证来源；录制回放层；出口代理；依赖安装隔离；组件版本锁定/传播/回滚协议；组件级签名；login→凭证落库；waiting_user 超时/崩溃恢复；DAG 幂等；用户运行上报 schema/同意/隐私边界；通过率展示规范；Token 预算熔断；退款证据链；sidecar 生命周期；公钥轮换。


## 5. 需求澄清评审（metis）

### 表态
**支持积木化的动机，反对其当前形态，要求先跑两个实验再承诺方向。**
产品负责人诊断的病灶是真的，但积木化把两个独立问题混为一谈：
- **问题 A：上架无统计门槛**——与积木化无关，必须立刻做，做了之后现场 codegen 路线的可靠性问题缓解大半；
- **问题 B：创作范式方差大**——积木化是解法之一，成败取决于积木覆盖率（一个未被任何文档测量过的数）。
正确顺序：① 补基线测量 → ② 上架统计门槛 → ③ 覆盖率桌面实验 → ④ 达标才投入积木库与录制。

### 隐藏意图与未明说的假设（8 条）
1. "测试通过"没有定义，平台侧认证环节在架构里根本不存在（M09 悬空）；
2. 健康评分混合三种不可比口径——沙箱测的是没有登录、没有交互的阉割版产品，买家跑的是完整版；
3. **"创作者"在两类人之间反复横跳，这是全文档最深的裂缝**——"说一句话"（非技术）vs "手动改代码 / requirements.txt / Monaco Editor"（技术）。积木化的真实前提是拆成积木贡献者（技术）与应用组装者（非技术），文档从未承认；
4. 旗舰卖点与唯一演示案例自相矛盾——《小红书选品助手》恰好落在 best-effort 类目，招牌案例本身落在承诺失效区；
5. 创作者 Token 经济学完全缺席（单位经济模型全文为零，若是负的，供给侧第一天就是死的）；
6. "平台不经手模型调用"与平台自身大量 LLM 消耗矛盾（自修复、归因、Marketplace Skill 都是平台侧调用）；Health 沙箱跑含 AI 组件用谁的 Key？
7. 隐藏假设：买家全程守在屏幕前——这实际是"有人值守自动化"；超时 600s，用户倒杯水任务就死了；
8. 数据飞轮的上传边界（review 交互的 items 就是买家业务数据）与冷启动（飞轮排阶段 4，selector 漂移阶段 1 就爆发）被刻意略过。

### 模糊地带（15 条精选）
认证沙箱登录态来源；"实测通过率"的样本量/环境矩阵/费用归属；**Agent 生成代码的知识产权（.aapkg 内含 main.py——买家买断即得全部源码，可改卖可抄袭）**；录制在现有架构零挂点（adapter 无 recording 类型，是范式替换而非增强）；非确定性输出如何断言 expected_output（没有断言规范，重试 25 次只是掷 25 次骰子）；失败指纹算法未定义；"交互兼容性校验"无可实现定义；节点副作用幂等；买断版本与健康检测版本错配；保证金没收与个税代扣合规；反爬对抗责任归属；健康沙箱（Linux 容器）与买家环境（Win/macOS）生态效度；文档自相矛盾两处；pick/takeover 交互是否该有"半成品"分级；探针触发封号的责任归属与频控。

### 过度设计清单（AI-slop）
1. **六库数据飞轮**——五个库没有写明消费者，砍到一库（selector 漂移→自修复）；
2. **WASM/Docker Adapter**——简历驱动设计，买家装 Docker 是荒诞的；python+agent 覆盖 95% 需求；
3. **L0-L5 反检测分层**——博客级分类法，L3 代理无归属且与"本机 Runtime、住宅 IP"部署模型冲突；
4. **三框架编排层**（LangGraph + OpenHands + langgraph-codeact）——选一个；
5. **8 种交互类型**——login/captcha/pick/takeover 四种控件实现相同，一种实现戴四顶帽子；
6. **Component Marketplace**——第一市场未验证就建第二市场；
7. **可观测全家桶**——几十个应用的体量用不上 Prometheus+Grafana；
8. **"健康覆盖率 100%"**——分母可操纵的虚荣指标（被"部分检测"的应用也算覆盖）；
9. **状态虚标"定稿"**——§13 含占位符、M09 悬空、§0 与 §14 矛盾，这不是定稿是评审中草稿。

### 缺失的验收标准
§13 现有指标全部不可测量或不可归因（无测量位置、无样本窗口、无归因分类、多数无目标值）。**决定成败却完全缺席的指标**：
1. **买家侧首次运行成功率**（第一卖点的直接度量，全文档最响的沉默）——按站点分级分桶，含登录工具单列；
2. **创作成功率**（"说一句话"→保存模块的会话占比；若只有 30%，供给侧胎死腹中）；
3. 创作耗时与 Token 成本分布（p50/p95）；
4. 重试预算消耗分布（25 次触顶率）；
5. **积木覆盖率**（积木化生死指标：<60% 则积木化只是给随机变量套中间件）；
6. 认证通过率 vs 上架后 30 天野外出错率的相关性（否则门槛是仪式）；
7. Health 归因 unknown 占比（>30% 则自修复链空转）；
8. Health 检测单次成本与月度总成本。

### 5 个最尖锐的问题
1. 创作者拆分，认还是不认？
2. 登录态认证悖论三条出路选哪条？
3. 敢不敢把旗舰承诺写成一个数？
4. 有人值守还是无人值守？
5. 先跑覆盖率实验，还是先承诺积木化？


## 6. 法务评审（legal-compliance）

### 已有的合规资产（必须保留，是防线不是包袱）
验证码一律转人工；凭证仅存本机、可撤销；高风险动作强制 confirm；**Token 完全用户自付、平台不经手模型调用（规避"生成式 AI 服务提供者"认定的关键架构，任何情况下不改）**；登录态组件仅公开页探活；信任字段主动披露；签名+审核+脱敏。

### 【高危】

**H1 针对强反爬站点的自动化抓取**
法律依据：反不正当竞争法互联网专条、刑法 285 条第 2 款、数据安全法 32 条、个保法、网络数据安全管理条例、平台用户协议。
**平台服务端 Health 沙箱对强反爬站点 6h 一次的自动检测，使平台自身成为高频自动化访问主体——文档中最直接的暴露点。**
改法：① 上架准入加"目标站点合规声明"审核项（强反爬 + 个人信息输出 + 对外发布三要素叠加重点审核）；② **high/extreme 站点取消服务端定时全量检测，改为创作者手动触发 + 用户运行上报聚合**；③ 探针礼仪默认化（公开页、低频、单会话、robots）；④ 输出物个人信息默认脱敏；⑤ 用户协议明确第三方站点合规责任归用户。

**H2 自动发布评论（AI 生成内容对外发布）**
法律依据：AI 生成合成内容标识办法（2025-09 施行）、生成式 AI 暂行办法、深度合成规定、跟帖评论规定、反不正当竞争法虚假宣传。
**PRD 3.4 / 8.1 以"发布评论"作示范用例，一旦发生刷评事件即"平台明知并推广该用途"的书面证据。**
改法：① lint 规则："发布类调用而无 confirm 交互声明 → 审核不通过"；② 信任字段加"含 AI 生成内容"标注；③ 示例改写为"生成评论草稿，经用户逐次确认后提交"；④ 协议负面清单（刷单、水军、批量营销评论）。

**H3 反检测工具链的定性风险与文档证据风险**
法律依据：刑法 285 条第 3 款（提供专门性程序工具罪）、287 条之二（帮信罪）、反法互联网专条帮助型。
**L1 指纹一致性 + L2 行为模拟的存在本身就是"明知并规避风控"的主观故意证明；文档措辞在被调取时即书面证据，无法事后辩解。措辞治理必须覆盖内部文档、代码注释、错误码、UI 文案、commit message。**
改法：① 词汇全面治理（14 条对照表见下）；② 站点指纹库删"反爬策略"类字段，只存结构性字段（功能不受损——该库用途就是 selector 修复）；③ 站点分级语义从"反爬强度"改为"页面结构变更频率"（工程上更准确，法律上更安全）；④ 探针限定目标域名 + 频次上限；⑤ 对外统一口径"本地浏览器自动化运行时（RPA）"。

### 【中危】
- **M1 经营资质**：撮合抽成大概率落入 EDI 经营范围。上线前资质清单前置（ICP 备案 + EDI 评估）；创作者提现前实名；交易记录保存 ≥3 年。
- **M2 保证金条款**："转没收"+ 失效未定义归因 → 格式条款大概率被民法典 496/497 挑战。**改法（30/70 与 20%/6 个月结构完全保留）**："转没收"改为"失效期间未释放份额转入平台保障金池，专项用于买家赔付与修复激励"；失效归因分级——站点改版（非创作者过错）暂停不转入，创作者失职才转入；台账增加 disputed 状态与申诉流程；购买页加数字商品确认勾选。
- **M3 凭证与登录态代操作**：用户本机+本人授权的操作与"非法侵入"有本质区别；真实风险是账号风控连累用户与凭证外传。改：授权页按站点展示操作类型清单 + 账号风险告知文案 + credential 句柄出现在网络请求体即拒绝上架（一票否决）。
- **M4 恶意组件分发**：审核记录 + 自动测试报告随版本归档（核心抗辩材料）；下架应急 SOP；详情页加"审核范围说明"（不构成运行结果担保）。
- **M5 生成式 AI 定性与数据出境**：平台不经手模型调用使平台难以被认定为服务提供者——**列为架构红线**；残余风险是用户自选境外模型的数据出境，引导页加一行提示。
- **M6 协议三件套缺失**：用户协议、隐私政策、创作者协议是上线前置缺口；注册环节年龄声明；interactions 表数据留存策略。

### 【低危】
L1 "买到就能直接运行"与 best-effort 现实落差过大有虚假宣传边缘风险——口号保留为愿景语，交易决策页固定展示"以信任字段为准"脚注。L2 开源许可合规（MIT/Apache/BSD + NOTICE 机制已有）。

## 7. 交叉分析：评审之间的冲突与联动

### 7.1 认证执行位置：服务端沙箱 vs 平台法律暴露【最重要】
- 架构师 F2/清单#4：服务端认证流水线（干净沙箱实测 N 次）；
- 法务 H1：服务端对强反爬站点的高频自动化访问是平台最大的法律暴露；
- 三方共识 2.2：登录类工具在服务端沙箱原理上不可测。
- **综合解法——认证分级执行**：
  - low/mid 站点 → 服务端沙箱认证（法务风险低，环境代表性可接受）；
  - **登录类/强反爬类 → 创作者本机认证 + 结果签名上报 + 服务端抽查复核**（方案①）。
  - 一石二鸟：同时解决登录态悖论与平台暴露；架构师标注其为"过渡方案、成本最小"；平台测试账号池（方案②）降级为"仅在与站点方有合作授权时考虑"。

### 7.2 种子积木库的站点选择
产品经理建议阶段 1 平台自营 20-30 个头部站点积木；法务指出平台集中维护对抗性资产是指纹库/证据风险的最大化。**积木库的站点优先级应按"法务安全度 × 使用频率"双维度排序**；强反爬站点的积木如做，必须完成措辞治理（结构化执行、页面结构特征库）后以中性名义存在，且优先考虑站点合作授权路径。

### 7.3 保证金与维护期（产品 F3 × 法务 M2）
合并解法：买断含 12 个月维护期（详情页公示截止日）；失效按归因分级——站点改版暂停释放不转入保障池，创作者失职转入保障池；"转没收"措辞从全部文档消失；平台积木缺陷导致的失效不罚创作者（权责对等，积木化后平台必须认平台侧责任）。

### 7.4 措辞治理可立即执行
法务 14 条对照表零功能损失、不依赖任何技术决策，可与任何方向并行，建议作为第一份落地改动。注意同步清理代码注释与 commit message，内部保留"术语映射表"。

### 7.5 指标与归因（澄清 × 产品）
两份评审都指向同一件事：§13 的指标缺测量位置、样本窗口、归因分类、目标值四要素。改法统一：每个指标必须写明测量位置（客户端上报/沙箱/服务端）、样本窗口、归因分类（复用架构附录 D failure_class 六类并扩展 user-side 类）、目标值。新增北极星：买家首次运行成功率（按站点分级）、30 天退款率。

### 7.6 问题 A 与问题 B 解耦（澄清 × 产品 × 架构）
- **问题 A（上架无统计门槛）**：与积木化无关，无条件立即做——连续 k 次通过（零基础设施）先行；
- **问题 B（创作范式积木化）**：以覆盖率实验（30-50 个真实创作需求，能被积木+参数化覆盖多少）为 gate，<60% 则积木化退化为"给随机变量套中间件"。
